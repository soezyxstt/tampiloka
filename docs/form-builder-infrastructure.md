# Form builder infrastructure handoff

The dedicated Neon project `rapid-lake-09427207` is in `aws-ap-southeast-1`. Its `production` and `development` branches each have a private `form-uploads` bucket and separate branch-scoped credentials. The Vercel project is `tampiloka` (root `apps/tampiloka`, verified production domain `tampiloka.site`). CMS database and storage credentials and a Better Auth secret have been set on production and separate development/preview targets; Google OAuth and allowlist remain unset. `apps/tampiloka/.env.prod` is ignored and holds the matching production values. It is not loaded by Next.js automatically: explicitly load it only for a deliberate production-like command; never use it for ordinary development.

The backend schema now exposes nullable `revisionId` and `questionId`; submission verifies both. Authorization serializes on the form row, validates the published revision and question, caps each file at 20 MiB, each session at 20 files/100 MiB and each question at its configured count, and issues a five-minute signed POST with an exact content-length policy. Completion copies to a new secret key and HEAD-checks the copied size/type, so a replay of the POST cannot overwrite an accepted file. The development bucket ignored a deliberately invalid `CopySourceIfMatch` during testing; do not rely on that precondition. Admin uploads require a session and form ownership; admin downloads return a 60-second private URL. Original incoming objects persist until cleanup.

Renderer integration: `FileUpload` takes `question`, `slug`, `revisionId`, `uploadSessionId` (a v4 UUID shared with submit), `value`, `onChange`, and `onUploadingChange`. Disable navigation and submission while any upload is in progress. The renderer lane owns the integration. Admin upload API uses POST `/api/admin/uploads` with `{action:'start',formId,filename,contentType,size}` and then `{action:'complete',formId,assetId}`; the start result contains `url` and `fields` for a multipart POST. Public upload uses the same actions at `/api/forms/[slug]/uploads` with `revisionId`, `questionId`, and `uploadSessionId`. Completion returns only the asset ID. File IDs and response files must never be exposed through a public asset route. Published header/logo/question images still need an authorization-aware public image route that verifies they occur in the currently published schema; the admin editor needs to call the admin upload API.

`scripts/cleanup-form-uploads.mjs` is dry-run by default; after inspecting its target environment, use `--apply` to delete pending assets and unattached respondent uploads older than 24 hours plus old incoming objects. Admin uploaded assets and attached response files are retained. This must be scheduled and monitored; no scheduler has been configured. Failed storage copies or database commits can leave orphaned final objects and require separate reconciliation; do not automatically remove objects referenced by a draft, revision or submission. No automatic deletion policy exists for archived/deleted forms. The client remove button removes the answer locally; its unused storage reservation persists until cleanup.

Preview uses the isolated development branch. `BETTER_AUTH_URL` is configured for production and local development only: a stable preview URL and OAuth redirect registration remain necessary before preview authentication or origin-checked uploads work. Production `.env.prod` is ignored by Git but deployment archive exclusion has not been verified. Ensure it is excluded before any deployment.

Neon supports private buckets, path-style S3, presigned PUT/POST and CORS; lifecycle rules are not enforced. Production CORS permits `https://tampiloka.site`; development permits localhost:3000 and Vercel preview origins. Configuration was read back; development signed POST, exact-size rejection, HEAD, and anonymous read denial were verified. MIME type is client supplied and no malware scanning or file-content sniffing is implemented. The rate limiter and per-session limits do not prevent distributed abuse or unlimited new sessions; production requires additional abuse controls, storage monitoring and a scanning/quarantine decision. Sources: https://neon.com/docs/storage/s3-compatibility and https://neon.com/docs/storage/buckets.
