# Form builder operations

`/api/cron/form-maintenance` is configured for 02:00 UTC daily (09:00 Jakarta). It is not active until a reviewed production deployment includes the route and `vercel.json`. Vercel sends `CRON_SECRET` as a Bearer token; missing, short or incorrect credentials receive 401. Responses contain no data. A 32-byte random secret is stored in ignored `apps/tampiloka/.env.prod` and as a production secret in the verified `tampiloka` Vercel project. Do not print it or add it to preview. On Hobby, scheduling may occur within the hour. Vercel does not automatically retry a failed invocation; monitor logs for the generic failure and retry through an authorized operator or wait for the next scheduled run.

A submission or form soft-deleted for at least 30 days becomes eligible for permanent deletion. The daily job starts afterwards; completion is not guaranteed exactly at 30 days or even at the next run. Backlogs, batch limits, outages and retries can delay it by multiple days. Deleting a form also deletes its submissions, revisions, slugs and associated stored files. Failed object deletion rolls back database reference changes so a later run can retry. Objects already deleted before a subsequent failure cannot be restored merely because their references remain. Soft-deleted responses are inaccessible in the application during this interval.

Pending uploads and unattached respondent uploads, including deleted-state uploads, become eligible after 24 hours; submission-linked assets are excluded. Old `incoming/` and `objects/` keys are scanned in bounded pages with a persisted cursor. A key must be at least 24 hours old and have no matching `assets.object_key` immediately before deletion. An asset in any state protects its object, including draft, revision and submission assets. This grace exceeds the 15-minute completion window and final keys are randomly generated, permitting recovery from interrupted completion.

Each run uses a database advisory transaction lock, a 40-second work deadline, database statement timeouts and bounded storage requests. Batches process at most four stale asset rows, ten objects per prefix, and five forms; each form processes at most one response and four files. Failure returns 500 and unfinished work remains eligible. Sustained intake or a large backlog can exceed this throughput and needs operator attention.

The operator scripts default to dry-run: `node scripts/cleanup-form-uploads.mjs` and `node scripts/purge-form-retention.mjs`. Set the explicit CMS database and storage environment first; use `--apply` only after verifying the target and reviewing eligible data. `.env.prod` is not loaded automatically by Next.js. For an intentional production dry-run, run `node --env-file=.env.prod scripts/cleanup-form-uploads.mjs` from `apps/tampiloka`. Never print credentials. Both scripts share the cron implementation and lock. A dry-run checks connectivity and selection, not deletion.
